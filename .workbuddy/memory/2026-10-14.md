  - 引入 ws 服务端 = **破「零依赖」红线**（`relay-server/package.json` 不得新增 deps 是硬约束；Node 裸 http 手写 WS 握手 + 帧解析 = 数百行且要处理掩码/分片/ping-pong，性价比极低）。
  - 现在的客户端是**手机浏览器**，可能走代理/企业网，ws 在某些代理下不如普通 HTTP 长轮询稳。
- **真正想「彻底事件化」的正确路径不是换协议，而是 P0-a 的 `notify()`** —— 长轮询**本来就挂在服务器上**，服务器随时可以提前结束它，这在延迟上等价于 ws 推送（亚秒级），却零依赖、零 CSP 风险、零兼容性破坏。这正是原报告的核心洞察，比换协议更优。
- 一句话给用户：**换 WebSocket 是「为了省轮询而去改协议」，但真正的省法是「让服务器主动结束已有的长轮询」；后者不破任何红线，前者破两条（CSP + 零依赖）。**

## 22:12 「长轮询 + notify() 会不会请求很多？」答疑（**无代码改动**）

用户担心 notify() 会推高请求数。**结论：不会，反而从 11664 降到 ~5904。**

- **关键洞察：notify 不是新机制 —— 现状 `deliver()` 早就在做「提前结束长轮询」**（消息到达即 `sendJson` 收尾，客户端 `poll()` 立刻重连）。它跑了很久，没人觉得请求多。notify 只是把同一动作**扩展到手机上下线事件**，复用同一套机制。
- **长轮询是闭环**：1 个请求 = 「要么等到消息（早返回）、要么等满 maxwait」，返回后立刻发下一个。⇒ **8h 请求数 ≈ 时长 / maxwait，与「期间来多少消息」无关**。真实上界 = `max(时长/等待时间, 消息条数)`，不可能爆炸。
- **notify 的额外开销极小**：notify 只在手机**上线/下线**时触发，每次只打断**当时在途的那 1 条**长轮询（每条 `/recv` 同时只有 1 个在途）。手机一天上下线 0~60 次 ⇒ 额外 +0~60 次。对比删掉的 `/phone/status` 5760 次，占比 ≤1%。
- **净账（8h / 1 电脑 + 1 手机）**：`/phone/status` 5760→0（改按需，一天几十次忽略）；`/recv` 1152（不变）；心跳 3600（不变）；`/phone/recv` 1152（不变）。**合计 11664 → 5904**。
- ⚠️ **唯一会推高请求数的情况**：`notify()` **触发过于频繁**（如每次心跳都 notify、或对每个等待连接都 notify 一遍）。⇒ 实现红线：**只在 `wasOnline` 状态翻转（上线）与 sweep 判定离线时各 notify 一次**，绝不在心跳循环里调；`notify` 一次只打断当时在途的等待连接，不要重复唤醒。

## 22:35 ⚠️ 跨世界测量陷阱（实验方法论，务必记住）

对照实验第一版整个 probe **只有 `main_*` 键、`iso_*` 全无**，差点误判「扩展根本没注入」。真因：**隔离世界的 `window` 与主世界是两个不同的对象**，content script 写 `window.__X__`，主世界 `page.evaluate` 读不到（反之亦然）。
- ✅ 正解：`document.dispatchEvent(new CustomEvent('tag', { detail: JSON.stringify(...) }))` —— **DOM 是两世界共享的**，用事件跨世界回传。
- 凡「隔离世界 vs 主世界」的对照实验，结果表里**必须有一条自校验键**（如 `iso_seesWindowMarker === undefined`）证明测的确实是隔离世界，否则整张表都不可信。
- `headless:true` 下扩展偶发不注入 ⇒ 每次跑都加 `--user-data-dir=profile-<timestamp>` 全新 profile，并延长等待到 2500ms 才稳定复现。
