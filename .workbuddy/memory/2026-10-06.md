## 排查：收到图片后「单击放大」有时长时间不显示（根因已定位，尚未修）

**现象**：收到图片后单击缩略图放大，有时要等很久才显示（用户报告）。

**根因（实验证实）**：`gallery.ts` 用 MutationObserver 把 Viewer 的 `.viewer-container` 移入画廊
overlay —— 这是 v26.7.29-v10 为修「预览跑到弹窗后面」引入的。而 Viewer.js 的 `shown()`
（设置 `isShown=true`、创建主图、`render()`+`bind()`）**只由容器的 `transitionend` 触发**
（viewer.js:2121-2140：`addListener(viewer, EVENT_TRANSITION_END, shown)`）。**移动 DOM 节点会打断
正在进行的 CSS 过渡 → `transitionend` 不再触发 → `shown()` 永不执行**：

- `isShown` 永远 `false` → 之后每次 `view()` 都在 viewer.js:2243 / 2276 提前 `return`
  → **主图从不被创建**（`.viewer-canvas` 一直为空）；
- `this.showing` 也永远停在 `true`（只在 `shown()` 里清）→ 反复点击无效，形成死锁。

**为什么是"有时候"**：这是「移动容器」与「过渡启动」之间的**竞态**。移动发生在过渡开始之前 →
过渡在新父节点里正常跑完 → 正常显示；移动落在过渡进行中 → 过渡被打断 → 卡死，只能等画廊因
新图重建 / 关闭重开才恢复，表现为"等很久"。

**实验证据**（`tmp/viewer-latency.js` + `tmp/viewer-latency.html`：真实鼠标点击 + 真实 `@require` 依赖 + 真实长轮询节奏）：

| 场景 | 主图首次出现 | Viewer 内部状态 |
|---|---|---|
| `transition` 默认 | **4 秒内从未出现** | `isShown:false`、`canvasKids:0`、`image:null`、无异常 |
| `transition:false` | **22ms**（4000×3000 / 854KB 为 29ms） | `isShown:true`、`canvasKids:1`、`src=blob:` |

**排除的假设**：
- ❌ 图片体积/解码：854KB 的 4000×3000 图 `decode()` 仅 **25ms**，与延迟无关。
- ❌ MutationObserver 的全文档查询开销：用真实长轮询节奏实测，整个窗口只有 **2 次**
  `.viewer-container` 查询（早期看到的"1400 次"是探针自己的 `querySelector` 被计入）。
- ❌ 非受信任合成点击：改用真实 `page.mouse.click` 后现象完全一致。

**建议修法（已实验验证有效）**：`new Viewer(...)` 传 `transition: false` —— `show()` 会走
viewer.js:2137-2139 的 else 分支**同步调用 `shown()`**，彻底消除竞态（代价：失去淡入动画；
`hide()` 同理变同步，顺带消掉关闭侧的对称风险）。改前须遵守 AGENT.md 约束 3（弹窗 CSS/Viewer
接管逻辑是实测结论），并跑 `npm run verify`。

### 修复：图片「复制」写不进剪贴板（v26.10.06-v4）+ 主页改 GitHub

用户报告：点画廊「复制」没有把图片写进剪贴板。要求参考 belingud/GM.UserScript、qsniyg/maxurl 重写。

**根因（按规范推导 + 实测能力佐证；本机 headless 无法复现真相，见下）**：
1. Chromium 的异步剪贴板**只支持写 `image/png`** —— 实测 `ClipboardItem.supports('image/jpeg') === false`；
   手机传来的图是 jpeg ⇒ 旧实现「**先按原图类型写一次**」的第一次调用**注定失败**。
2. 按规范，`clipboard.write()` 通过用户手势校验后即**消耗**该手势（失败也不退还）
   ⇒ 转 PNG 后的第二次重试必然 `NotAllowedError: Write permission denied`。
   旧实现正是这个顺序（实测两次尝试间隔约 1s，正好是异步转 PNG 的耗时）。
3. 新实现：**先转好 PNG → 只写一次**；用 `ClipboardItem` 的 **Promise 形式**让 `write()` 落在点击手势内
   （异步转换耗时不再影响手势有效性）；写入走**页面主世界**（`unsafeWindow`）；用该 realm 的
   **原生 Blob 构造器**重新包一层（跨 realm 直接传 Blob 会被拒）。

**参考实现**：把 maxurl 下载到 `tmp/` 后用 grep 定位（不占上下文）——它**只调用一次 write**、
用页面原生 `native_blob` 构造 ClipboardItem、异常分支齐全。本脚本**不需要**它「跨域图片经
`GM_xmlhttpRequest` 取二进制」那一段（图片本来就是中继传进来的 Blob）。

**⚠️ headless 环境无法复现真相**：写了最小对照实验 `tmp/clipboard-activation.js` ——
**A 组「直接写一次 `image/png`」也被拒** `NotAllowedError`，说明该环境根本写不了图片剪贴板，
**不能据它判定代码对错**。所以改为「按规范推导根因 + 用能在 headless 生效的不变量做回归」。

**新增断言**：`npm run verify` 第 9 项「图片复制只尝试写 PNG」——在页面里桩掉
`Clipboard.prototype.write` 只记录条目类型，断言「至少发起过一次写入，且类型**只有** `image/png`」。
反向验证：把产物里所有 `image/png` 替换成 `image/jpeg`（模拟旧行为）→ ❌；还原 → ✅（逐字节比对）。

**主页**：`@homepageURL` 与面板 `[脚本主页]` 按钮都改为 `https://github.com/Run-os/znhd-service`。

**踩坑**：① `navigator.clipboard.write` 用真值判断会被 **TS2774** 拦（函数属性恒真），
必须写 `typeof navigator.clipboard.write === 'function'`；② 本项目 webpack 用 **ts-loader**，
所以 `npm run build` 也会因 TS 错误失败（不只是 `typecheck`）；③ 断言里 `i.types` 是数组，
取 MIME 要多剥一层（`rec[0][0]`），少剥一层会导致断言自己误判。

### 2026-10-06 · 复盘 antd 官方博客《打包体积优化》对本项目的适用性（未改代码）

用户给了 https://ant-design.antgroup.com/docs/blog/tree-shaking-cn（站点页抓不到正文，**源仓库 raw 才有全文**：
`ant-design/ant-design/docs/blog/tree-shaking.zh-CN.md`）。

**博客要点**：Tree Shaking 是**静态**过程，运行时配置无法参与优化。具体案例：`ConfigProvider` 为支持
`form={{ validateMessages }}` 而静态依赖 `rc-field-form` 的 `FormProvider`，导致**没用 Form 的项目也把整条
rc-field-form 依赖打进产物**；因为 `validateMessages` 是运行时 prop，无法用「没传就不渲染」来规避。
根治办法是把这条依赖**解耦**（抽一个 ValidateMessageContext 代理，ConfigProvider 不再感知 FormProvider）。

**对我们是否适用**：
- 我们用的是 **antd 6.6.5**，该问题在 5.x 期间就已修复（博客日期 2023-06，早于我们的版本），**理论上不适用**。
- 但「有没有真被牵连」要用产物说话。我尝试用 webpack stats 统计"真正进入 chunk 的模块"，
  **两次都失真**：一次漏了 `nestedModules`（拼接模块的子模块没展开，全部算成"本项目源码"），
  一次加上之后总量只剩 3KB。原因是 `optimization.concatenateModules` 把大量模块合并成一个
  以 `./src/index.ts + N modules` 命名的模块，按 `name` 匹配 `node_modules` 归属会失效。
  → **结论：没有拿到可信的按包占比，不据此下结论。** 要拿到确定性结论，应改用
  `webpack-bundle-analyzer`，或做「去掉 ConfigProvider 的对照构建」比体积。
- 已知可信的两点：① 之前用「未使用组件是否出现在产物里」的探针（搜 `ant-table`/`ant-transfer`/`ant-date-picker`/`ant-calendar`/`ant-carousel`/`ant-tree`/`ant-upload` 等）**全部未命中**，说明 tree-shaking 在起作用；② 该探针**有假阴性风险**——反例：`ant-btn`/`ant-progress`/`ant-switch`（明明用了）也搜不到，因为 antd v6 的类名前缀多为运行时拼装（`getPrefixCls('btn')`），不是字符串字面量。**所以「搜不到」不能证明「没打包」，这个探针以后不要再用。**

**结论与建议**：当前产物 0.772 MiB / gzip 257 KB，构成是「React 19 + 实际用到的 ~14 个 antd 组件 + cssinjs 引擎」，
没有可一刀切掉的整块依赖。继续压只剩「减少使用 antd 组件」这条路（例如收图画廊的 `Image.PreviewGroup`、
手机弹窗的 `Progress`），代价是牺牲刚统一的 antd 一致性，**收益有限、不值得**。建议到此为止。
