
## relay-server/server.js 新一轮代码审查（子代理，结论已回报父会话）

- 本地实测（Node 25，端口 5699）：413 溢出路径正确（超限 body 读到 end 后回 JSON 413，keep-alive 连接可复用）；心跳 POST body 未 req.resume() 但连接仍复用（body 与头同包到达即视为已消费，无需改）；客户端断开 mid-body 未崩溃。
- 新发现（重点）：① readBody 无超时——stalled POST body（声明 Content-Length 不发完）实测 5s+ 无响应；Node 14（engines 声明 >=14）requestTimeout 默认 0 = 无限挂起。建议 readBody 内加 30-60s 超时 reject+destroy，或显式设 server.requestTimeout。② 手机页 recvItems 无上限（脚本端 MAX_GALLERY=27），长开页内存无界。③ 手机页 copyRecvImage 未转 PNG——本仓库自有结论「Chromium 剪贴板只可靠支持 PNG」未应用到手机页。④ pollRecv 无看门狗（heartbeat 有 8s race，pollRecv 没有），移动系统挂起后 fetch 可能永不定型→收图静默停摆。⑤ deploy.yml 健康检查失败不 exit 1，且「容器内版本比对」读的是 tar 刚写入的 /app/package.json（近乎恒真）——服务崩溃时 job 仍绿；建议 /health 的 version 与期望值比对并失败退出。⑥ deploy.yml 无 concurrency group、无 pipefail、release 触发也部署 main。
- 小项：HEAD /u/<id>→405 无 Allow 头；POST /recv→404 非 405；removeRecvItem 删最后一张后 recvBtn 计数残留；downloadRecvImage 丢原名、svg+xml 扩展名怪；relay-server/package-lock.json version 停在 1.0.0（实际 26.9.6-v2）；ReadMe 常用语清单两个「5.」。
- deliver() 已知丢条窗口确认在 server.js L116（q.shift()）先于 L119（writable 过滤）。
