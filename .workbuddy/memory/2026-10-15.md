## 00:10 P3 落地：长轮询挂起时长 25s → 45s（脚本 v26.10.15-v1 / relay v26.10.15-v1）

**背景**：轮询优化第三批 P3。任务书要求「改前必须先确认线上 nginx `proxy_read_timeout`」，本次**实测确认**。

### 🔑 服务器事实（新知识，下次直接用）

- znhd 部署在 **极点云-HK**（`45.207.199.216:65000`，OneSSH 可达；`~/.workbuddy` 里没有这台，走 `mcp__onessh__` 的 host 名 `极点云-HK`）。
- **反代是 1Panel 的 openresty 容器**（`1Panel-openresty-AP4d`），**不是宿主机 nginx** —— 宿主机 `/etc/nginx/` 里根本没有 znhd（踩过一次：在宿主机 `grep znhd /etc/nginx/` 全空）。
- 容器挂载：`/opt/1panel/1panel/www` → `/www`；`/opt/1panel/apps/openresty/openresty/conf/*` → `/usr/local/openresty/nginx/conf/*`；`conf.d` 实际在 `/opt/1panel/1panel/www/conf.d`。
- 站点块 `/opt/1panel/1panel/www/conf.d/znhd.122050.xyz.conf`：只有 `location / { ... proxy_pass http://127.0.0.1:5689; }`，**没有任何 proxy_read_timeout 覆盖**。
- **http 级 `proxy_read_timeout 3600s`**（`/opt/1panel/apps/openresty/openresty/conf/nginx.conf:49`，`proxy_send_timeout` 同值）⇒ 60s 挂起余量 59 倍。任务书担心的「nginx 默认 60s 撞线」在 1Panel 环境**不存在**。
- **实测手法**（走真实反代链路，不依赖外网 DNS）：
  `curl -s --resolve znhd.122050.xyz:443:127.0.0.1 -o /tmp/x -w 'HTTP=%{http_code} 耗时=%{time_total}s\n' 'https://znhd.122050.xyz/recv/<uuid>?maxwait=30000'`
  → `HTTP=200 耗时=30.132261s` + `{"empty":true}`。

### 改动（三处，纯参数）

- **中继** `relay-server/server.js` `handlePoll`：钳制 `[1000,30000]` → **`[1000,60000]`**。⚠️ **只放宽上限，默认值仍 25000** ⇒ 不带该参数的老客户端行为零变化。
- **脚本端** `src/lib/relay.ts`：稳态 `maxwait` 25000 → **45000**（首次仍 1000，只为快速确认「已连上」）；`timeout: maxwait + 5000` 自动跟随到 50000。
- **手机页** `web/src/lib/relay.ts`：`&maxwait=45000`；看门狗 35000 → **55000**（保持既有的 `maxwait + 10s` 节奏）。**需 `build:web``。
- 两端取 **45s 而非上限 60s**：给客户端 timeout 与反代各留余量。

### 收益

单人 8h 请求数 **~5904 → ~4880**（`/recv` 1152→640、`/phone/recv` 1152→640；心跳 3600 与 `/phone/status` ~0 不变）。

### 断言（relay +1 条）

`P3：/recv?maxwait=45000 未被钳到旧的 30000 上限（31s 后仍挂起；旧上限会在 30s 返回 empty）`

⚠️ **本仓唯一一条必须真等 31s 的断言**。理由：钳制值是常量，「上限 30000」与「上限 60000」之间**唯一**的可观测差异就是挂起时长（旧上限下 45000 会在第 30 秒被钳成 30000 而提前回 `{empty:true}`）。**没有更短的区分手段**（除非读源码文本，那就不是行为断言了）。
- 手法：探测 `recvPoll({device: P3_DEVICE, maxwait: 45000})` 在 `main()` **最早期**启动（紧跟 `console.log` 那行），与后面所有断言**并行**跑，末尾 `await sleep(Math.max(0, 31000 - (Date.now() - p3Start)))` 补足再判定，最后 `abort()`。净增约 28s。⚠️ 别写成串行 `await sleep(31000)`。
- **反向验证**：把中继钳制改回 `30000` ⇒ 断言如期变红（30s 就收到 `{empty:true}`，`isSettled()` 为 true），恢复 60000 后复绿。

## 01:40 P4 落地：心跳并入长轮询（脚本 v26.10.15-v2 / relay v26.10.15-v2）

轮询优化**最后一批**。手机端从「8s 心跳 + 45s 长轮询」两条连接 → **一条** `POST /phone/poll/<deviceId>`（body `{phoneId}`，报活 + 收件合一）。8h 请求数 **~4880 → ~1280**，**达成任务书「<1500 次/8h」的目标**。

### 改动

- **中继** `relay-server/server.js`：
  - 新路由 `/phone/poll`：解析 body 拿 phoneId → `touchPhone()` → `res.__recipient = phoneId` → `res.__pollAlive = phoneId` → `res.on('close', () => refreshPhone(...))` → 复用 `reverseChannel.handlePoll()`。
  - `handlePoll` 新增分支：**`res.__recipient` 已被路由预设就不再从 URL 取**（不加这行，新端点会因 URL 没有 phoneId 被 400 拒掉 —— 第一个坑）。
  - 新增 3 个函数：`touchPhone()`（与 heartbeat **共用**报活逻辑，抽出来防漂移）、`refreshPhone()`（close 时**静默**刷时间戳，不触发上线判定）、`pollAliveSet()`（挂起中的 poll 集合）。
- **在线判定语义变更（P4 唯一风险点）**：旧 = 「距上次心跳 < `PHONE_TTL`(20s)」；新 = 「**挂起中的 poll 算在线** + 断开后 TTL 判离线」。`listPhones`（名单构造）与周期清扫（`m.set(pid, now)` 续命）**两处都要判**；`refreshPhone` 补「返回 → 重连」的毫秒空窗。**只认 `__pollAlive`** ⇒ 老手机页的 `/phone/recv` 语义零变化。真离线仍 ~20~25s（**没退化**）。
- **手机端** `web/src/lib/relay.ts`：`pollRecv()` → `tick()`；新增 `mode: 'unknown'|'poll'|'legacy'` 状态机；`onConn` 改由长轮询驱动；删 `setInterval(heartbeat, 8000)`。
  - ⚠️ **未确认连上时用 1s 短 maxwait**（`confirmed` 标志 + 看门狗同步缩到 `maxwait+5000`）：否则「已连接」要等 45s（旧行为 ≤8s，明显退化）。实测 ~1s 内显示，比旧行为还快。
  - ⚠️ **404 降级**：老中继没有 `/phone/poll` ⇒ 切 `legacy` + `startHeartbeat()`，**只在 `mode==='unknown'` 时判**（锁定新模型后偶发 404 不来回横跳）。

### 断言

relay +8 条：老端点仍可用 / 有消息立即返回且**定向条目只给目标手机** / 非目标继续挂起 / 缺 phoneId 回 400 / 新端点也登记在线 / **挂起中超过 TTL 仍在线** / **只报活一次的手机照常判离线** / 无消息挂满 maxwait 回 empty。
手机页 +3 条：主页面 `poll>0 && heartbeat===0`（两个条件都要 —— 只判前者时「压根没连上」也过）；**用请求拦截把 `/phone/poll` 拦成 404 在本地造一个老中继**，断言先试过新端点、随后真发出 `/phone/heartbeat` + `/phone/recv`。

### ⚠️ 本次最大的坑：冗余双层 ⇒ 反向验证假绿（第二次踩）

`pollAliveSet` 被 `listPhones` 与 sweep **冗余使用**：只关 sweep 那一层时，`listPhones` 自己的 `alive.has(...)` 照样把手机算作在线 ⇒ 「挂起中的 poll 超过 PHONE_TTL 仍算在线」**仍全绿**（我一度以为改动没问题）。**必须两层同时关掉**该断言才如期变红，而「F 照常判离线」保持绿（1:1 对应）。
→ 这是本仓**第二次**踩「分层兜底 ⇒ 单点关闭不足以复现旧行为」（第一次是 v26.10.14-v5 sniffConv 的 `AliasTable`）。已进 AGENT.md 踩坑表。

### 测试窗口复用（省时间的关键）

P3 的 31s 挂起探测与 P4 的「越过 `PHONE_TTL`(20s)」边界**共用同一个等待窗口**（都在 `main()` 最早期启动、并行跑，末尾分别补足到 23s / 31s 判定）⇒ `verify:relay` 总时长仍是 **~38s**，没有变成 60s+。

### 验证

relay 8 条新断言全绿 + 既有 40 余条全绿（`relay:ALL-OK`）；手机页 3 条新断言全绿 + 既有 30 条全绿（`phone-page:ALL-OK`）。**反向验证**：两层同关 ⇒ 「挂起中仍在线」变红、另两条保持绿；恢复后复绿。

### 状态

任务书 P0~P5 **全部落地**：P0/P1/P2（v26.10.14-v7）+ P5（v8）+ P3（v26.10.15-v1）+ P4（v2）。请求数 11664 → **~1280**（-89%），手机上下线感知 **亚秒级**。
