## 修复图片复制到剪贴板失败 + 关闭按钮红圆（v26.7.26-v4）
- **根因**：`copyImageToClipboard` 原只走 `navigator.clipboard.write([new ClipboardItem(...)])`，但 ScriptCat 把脚本跑在**隔离世界**，其中 `ClipboardItem` 全局常 `undefined` → `typeof ClipboardItem!=='undefined'` 不成立 → 直接 `resolve(false)` → 弹窗"复制失败"。而文本复制（`safeCopyText`）因优先 `GM_setClipboard` 才可用——这就是图片不能复制的原因。
- **关键事实（已用 ScriptCat 官方 API 文档核实）**：`GM_setClipboard(data: string, info?)` **只接受字符串（文本）**，相比 Tampermonkey 不支持图片 Blob。故不能直接把 Blob 丢给 `GM_setClipboard` 当图片用。
- **修复**：`copyImageToClipboard` 改三级兜底：①`GM_setClipboard(blob,type)`（扩展特权，不支持图片时抛错降级）②**页面主世界 `unsafeWindow.navigator.clipboard.write` + `new unsafeWindow.ClipboardItem`**（HTTPS 页面下必定可用，且点击按钮的用户手势随调用保留——最可靠兜底）③原隔离世界写法。脚本已 `@grant unsafeWindow`。
- **红圆关闭按钮**：弹窗「×」`cssText` 改 `background:#e4393c;color:#fff;border-radius:50%`（红底白字圆），hover 加深 `#c9302c`。
- `@version`→`26.7.26-v4`；ReadMe 更新日志 v4 已同步。

## 修复「复制成功但剪贴板无图」假成功（v26.7.26-v6）
- **根因**：v5 把 `GM_setClipboard(png, type)` 作为图片复制**首选项**；但 ScriptCat 的 `GM_setClipboard(data:string)` 仅支持文本，传 Blob 时**不报错也不真正写图** → `resolve(true)` 误报成功，日志 `[复制] 图片已复制到剪贴板 (GM_setClipboard)`。剪贴板实际为空。
- **修复**：图片复制**唯一可靠路径 = 页面主世界 `unsafeWindow.navigator.clipboard.write`**（`attemptWriteImage()`：先 `unsafeWindow` 再退回隔离世界同名 API）。流程：①先用**原始 blob** 直接写（点击手势最新鲜、无异步转换）②失败再 `blobToPng` 转 PNG 重试③**彻底移除 `GM_setClipboard` 图片分支**（它是假成功元凶）。
- 弹窗「复制到剪贴板」按钮文案随真实 `ok` 变化：成功→绿色"已复制，去 Ctrl+V"；失败→"复制失败，请长按图片保存"。
- `@version`→`26.7.26-v6`；ReadMe 更新日志 v6 已同步。

## 点击复制卡顿的真正根因（v26.7.26-v8）
- 用户实测：手机上传图仅 **1600×100 / 410KB**，点「复制」仍长时间等待 → 证明瓶颈**不在图片尺寸/PNG 编码像素量**，而在**转换发生的时机**。
- **根因**：`copyImageToClipboard(img.blob)` 在**点击时**才跑 `createImageBitmap`+`canvas.toBlob`（jpeg→png 重编码），耗时全卡在「点击」与「已复制」之间；且此前「先试原图 jpeg」分支在 ScriptCat 内核（仅认 `image/png`）必失败再转 PNG，等于白等一轮。
- **修复**：把 PNG 预转换**提前到图片到达、弹窗显示时**（`showImagePopup` 内 `ensurePrepared()` 后台 `prepareClipboardImage` 并缓存）→ 点击时 `copyImageToClipboard` 仅做 `attemptWriteImage(blob,'image/png')` **直接写入、零转换、即时响应**。`prepareClipboardImage` 对已是 PNG 的图直接复用、不重编码。移除「先试 jpeg」浪费分支。
- `@version`→`26.7.26-v8`；ReadMe 更新日志 v8 已同步。
- **给用户的性能判断经验**：ScriptCat/Chromium 下"点复制才转码"是体验杀手；凡涉及 canvas/位图重编码，尽量在展示期预做、点击只做最终 I/O。

- **真因（非旧版、非 CAT_UI、非图片透明）**：现代 SPA（征纳互动即 Vue/React）常在 `body` 上施加 `transform`/`filter`/`will-change`/`contain`，会把 `position:fixed` 的**包含块改写**为 `body` 自身。原弹窗挂在 `document.body`，于是 `fixed` 不再相对视口、而是相对被 transform 的 `body`——遮罩被偏移/裁切（实测 `overlayRect.left≈529`、视口左上角不再被遮罩覆盖），两侧页面文字随之漏出。这完美解释「v12/v13 已加载、图片不透明、遮罩 `#000`+`!important` 却仍透字」。
- **browser-use 实测复现**：写 `tmp/popup_repro.html`（本地页，`body{transform:translateZ(0);max-width:700px;margin:0 auto}` 模拟 SPA 根），在连着的真实 Chrome 跑 `window.__test(where)`：
  - `where='body'` → `overlayRect={left:529,top:0,right:2303,bottom:955}`、`coverFull=false`、`cornerCovered=false`（**复现透字**）；
  - `where='html'`（documentElement）→ `overlayRect={left:0,top:0,right:1774,bottom:955}`、`coverFull=true`、`cornerCovered=true`（**修复**）。
- **修复**：`showImagePopup` 末尾 `document.body.appendChild(overlay)` 改为 `document.documentElement.appendChild(overlay)`。`documentElement`(<html>) 是 `body` 的父级、不在被 transform 的 `body` 子树内，`fixed` 重新相对视口定位。CAT_UI 面板半透明与此无关（其样式在 Shadow DOM 内且带 `.ar.co-` 前缀）。
- **诊断指标修正（重要）**：原 v13 诊断用「遮罩宽度==视口宽」判断铺满，会**漏报偏移**（宽度仍是 `100vw` 但 `left` 已不贴边）。v14 改为判定**四边是否贴住视口**（`left/top<=1 && right/bottom>=视口-1`）+ 视口左上角 `(3,3)` 是否被遮罩覆盖；warn 文案明确点出「祖先 transform/filter/will-change/contain 改写 fixed 包含块」。
- 顺带：弹窗版本标记由写死的 `v12` 改为 `v14`（与 `@version` 一致）。`@version`→`26.7.26-v14`；ReadMe v14 已同步；语法 `node -c` 通过。

## ⚠️ 真因推翻重来：弹窗“透字”= 遮罩 opacity:0.8（v26.7.26-v15，实测坐实）
- **v14 的 transform 偏移理论是错的**（被实测推翻）。用户在 example.com 上真触发了弹窗，我当场测量运行中弹窗：
  `runningPopupVersionMarker="znhd v26.7.26-v14"`、`overlayComputedOpacity="0.8"`、`overlayRect={l:0,t:0,r:1774,b:950}`（**已铺满视口**）、`bodyTransform:none`、`parent:<html>`。
  → 遮罩**已铺满、无 transform**，却仍透字 ⇒ 真因不是偏移，而是**遮罩自身 `opacity:0.8`**（黑底只盖 80%）。
- **关键 CSS 机制**：`opacity<1` 会把元素与**其全部后代压扁成同一层、同透明度**一起半透明——所以 overlay 0.8 → 内部白框/图片/按钮全跟着 0.8 → 一透全透。
- **运行版 ≠ 工作区文件**：我工作区 v14 的 overlay/box `cssText` 根本**没写 opacity**（某次编辑把 `opacity:1!important` 行弄丢了），本应默认 1；但用户跑的 v14 副本 overlay computed = 0.8 ⇒ 二者代码不一致（用户装的副本遮罩带 0.8）。这也解释了为何之前多版"改了没生效"——实际比对要量"运行中弹窗的计算样式"，不能只比对工作区文件。
- **修复（v15）**：给 `overlay`/`box`/`ver`/`close`/`copyBtn` 全部内联加 `opacity:1!important`（内联 !important 优先级最高，压过任何旧副本/全局 CSS）。
  **现场验证**：在运行中旧弹窗上 `ov.style.setProperty('opacity','1','important')`，计算透明度即时 `0.8 → 1`，证明修复有效。`@version`→`26.7.26-v15`；版本标记 `v15`；ReadMe v15 已同步（并更正 v14 条目为"防御性、非本 bug 真因"）。
- **方法论教训（最重要）**：userscript 弹窗 bug 排查，**别再靠"读代码猜"或"推断旧版在跑"**。直接连浏览器、量运行中弹窗的 `getComputedStyle(overlay)`（opacity/background/position）、`getBoundingClientRect()`（是否铺满）、`elementFromPoint` 四角/中心（谁在最顶）。本例从 v10 到 v14 一连串推断全错，直到 v15 才"量"出真因 `opacity:0.8`。example.com 是脚本 `@match` 测试页（第 8 行），**能复现弹窗**，应优先在此触发测量而非空谈。

## 修复"连上服务器"日志误报超时（v26.7.26-v20）

## 修复「刷新后第一次手机发图不弹窗、第二次才弹」(relay-server)
- **现象**：刷新税务页后，脚本生效，但手机第一次点发送图片通常不弹预览窗；第二次点发送才弹。
- **根因（relay-server/server.js 的 `/recv` 长轮询）**：服务端未检测客户端断连。刷新网页时，旧页面那条仍在「挂起」长轮询连接（25s 内持续 `setTimeout(tick,400)`）在服务端并未消失；此时手机发图，服务端 `tick` 可能把图片投递给这条**已失效的旧连接**，而旧连接的 `onload` 永不在新页面触发 → 第一张图「丢失」、弹窗不出现。若随机（race）命中旧连接即"通常"不弹；旧连接还可能在 `res.end()` 时向已关 socket 写数据抛未捕获异常使进程崩溃。
- **修复**：`/recv` 内 `req.on('close', () => closed = true)`，并在 `tick()` 顶部 `if (closed) return` 停止向失效连接投递；`sendJson` 包 `try/catch` 兜底。效果：刷新后旧连接一断开服务端立即停止其轮询，图片留在 `pending`（TTL 60s）被新连接取走 → 第一次发图即弹窗。
- **注意（给用户）**：此修复只在**中继服务器**侧，须**重启 `node server.js`** 才能生效（进程内 `pending`/连接状态不热更新）。社工脚本 `znhd.user.js` 未改动，无需重装/版本号递增。
